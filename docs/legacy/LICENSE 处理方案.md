# LICENSE 处理方案（T006 准备材料）

结论：**直接沿用现有仓库的 MIT 文本作为新工程的 LICENSE，不做改写、不新增第二个许可证。** 同时用 docs/legacy/ 说明把「新代码/自制素材」与「旧版代码/素材」的授权范围分开。本文只是决策与依据记录，真正的 LICENSE 文件已随本材料一并放入 staging（内容与当前仓库一致）。

## 1. 现状

| 项 | 内容 |
| --- | --- |
| 当前文件 | 仓库根目录 `LICENSE`，1067 字节 |
| 许可证 | MIT License |
| 版权行 | `Copyright (c) 2025 GuZhengSVT` |
| 引入提交 | `bb0d38c docs: split bilingual README, add MIT license and roadmap` |
| 与决策的关系 | 架构说明书 D-14：新代码与自制素材采用宽松、便于贡献与再分发的 MIT；不要求衍生项目必须开源；第三方依赖/字体保留各自许可；**旧代码/素材不因重写自动变成 MIT** |

结论：现有 LICENSE 与 D-14 想要的方向一致，无需更换许可证类型，也不存在「MIT 不允许闭源衍生」的障碍（MIT 允许）。

## 2. 处理方案

### 2.1 沿用 MIT 文本

新工程初始化时，把当前仓库的 MIT 文本原样放入根目录 `LICENSE`（本 staging 已包含一份，路径 `staging/LICENSE`）。理由：

1. 版权持有人未变（同一维护者 GuZhengSVT），重写不改变权利人，重新起草一份等同文本没有收益。
2. 许可证类型已由 D-14 批准，重写为另一种许可证会造成历史提交与新仓库之间的授权表述断层。
3. 保留原文便于与旧仓库的 `LICENSE` 逐字节比对，避免出现「看起来一样、实际有细微改动」的模糊状态。

### 2.2 年份处理（建议，不强制）

当前版权行为 `Copyright (c) 2025 GuZhengSVT`。若维护者希望体现新版的延续年份，可改为区间写法（例如 `2025-2026`）。**这属于维护者决定的可选项**：不改也不影响 MIT 有效性，因为 MIT 只要求保留版权声明本身，并未要求年份必须更新。主代理如需改动，请与维护者确认后再动，不要由子代理自行修改法律文本。

### 2.3 与旧素材的边界（D-14 落地）

MIT 文本只覆盖新工程自己的代码与自制素材。旧版 Flux 的代码、图片、图标等：

- 不因为「从同一个仓库重写」而自动转为 MIT；
- 按封存时的原有授权条件保留（封存动作见 T002）；
- 若旧素材的授权条件未知或不允许再分发，就不应复制进新工程，而应重做（这也是 D-13「模型可自行绘制原创 SVG」的落点）。

这条边界以草稿文档 `docs/legacy/README.md` 的形式给出，措辞明确写出「旧版素材版权归原权利人，不因重写自动转为 MIT」。该文件是**草稿**：仅提供文本，实际归档动作与旧版引用方式由主代理在 T002 完成后确认，避免出现「文档说已归档、实际未归档」的不实陈述。

### 2.4 第三方依赖与字体

新增依赖时，除 MIT 声明外还要：

1. 在依赖清单中记录每个直接依赖的许可证标识（如 MIT / BSD-3-Clause / Apache-2.0）；
2. 对 GPL/AGPL 或带额外限制的依赖**先停下评估**，不默认接受；
3. 商用字体、图标库单独记录许可证与使用范围，不随 MIT 一并授权；
4. 若在 M5 需要分发包内附带第三方许可文本，再在此方案基础上扩展，届时以实际依赖为准。

## 4. 未决项（需维护者/主代理确认）

1. 版权年份是否改为年份区间（见 2.2）。默认建议保持原样。
2. 旧版封存后的目录名与引用方式（`docs/legacy/` 与封存标签的对应关系），属于 T002 产出，本文只提供草稿措辞。
3. 首发是否需要随包分发第三方许可聚合文本，取决于 M5 实际依赖，暂不预设。

除以上三项外，本方案在 T006 不需要维护者再作决定即可执行。
